# 仕組み { #how-it-works }

!!! note ""
    このページは英語の原文を翻訳したものです。内容が異なる場合は[英語の原文](https://honeybee-studio.github.io/honeybeepf-llm/how-it-works/)が正しい内容です。

LLM プロバイダーを呼び出すアプリは、リクエストを平文のまま TLS ライブラリに渡し、レスポンスも平文で受け取ります。honeybeepf-llm は、その時点のバイト列のコピーを、ノード上で eBPF によって読み取ります。アプリ、その SDK、プロバイダーまでのネットワーク経路はそのままです。

![SSL_write/SSL_read の uprobe が平文をリングバッファーにコピーし、エージェントが HTTP を解析してプロバイダーを判定し、cgroup を Pod に対応付けて OTLP メトリクスをエクスポートする](../images/how-it-works.svg)

## 1. TLS のコードを見つける { #1-find-the-tls-code }

エージェントは DaemonSet として、ノードごとに 1 つの Pod で動きます。ノード上のすべてのプロセスを調べ、各プロセスが TLS を処理している場所を見つけます。

| プロセスの種類 | エージェントのアタッチ先 |
|---|---|
| 共有ライブラリの `libssl.so` をマップしている (Python、ディストリビューションのパッケージの Node.js、curl) | そのライブラリ内の `SSL_read`、`SSL_write` と、それぞれの `_ex` 版 |
| OpenSSL が実行ファイルに組み込まれている (公式の Node.js バイナリー) | 実行ファイル内の同じ関数 |
| Go 1.20 以降の実行ファイル | `crypto/tls` の `(*Conn).Write`、`Read`、および `Read` の各 return。Go の関数テーブルから見つけるため、strip されたバイナリーにも対応します |

後から起動したプロセスにもアタッチします。`exec` と `libssl` ファイルのオープンに仕掛けたプローブによって、新しいプロセスを検知します。rustls や Java の JSSE など、別の TLS スタックを使うプログラムはまだ観測できません。こうしたプログラムは[カバレッジメトリクス](guides/coverage.md)で一覧できます。

## 2. 平文をコピーする { #2-copy-the-plaintext }

各プローブは、関数の呼び出し時または return 時に実行される eBPF プログラムです。平文のバッファー (read は最大 16 KB、write は最大 4 KB)、プロセス ID、cgroup ID を、エージェントと共有するリングバッファーにコピーします。プログラムは読み取りしか行いません。呼び出し、データ、接続のいずれも変更しません。

Ollama や vLLM のように、クラスター内で平文の HTTP で呼び出すモデルサーバーには、フックできる TLS ライブラリがありません。`plaintext` を指定したプロバイダーについては、エージェントは代わりにソケットでバイト列をコピーします ([平文の HTTP で動くセルフホストモデル](guides/plaintext.md)を参照)。

## 3. バイト列を呼び出しに変換する { #3-turn-bytes-into-calls }

ユーザー空間では、エージェントが各接続のバイト列を HTTP/1.1 または HTTP/2 のリクエストとレスポンス、あるいは WebSocket のメッセージ (Realtime、Responses、Gemini Live) に再構成します。圧縮されていれば展開し (`gzip`、`br`、`zstd`、`deflate`)、Server-Sent Events のストリームは最後まで追います。リクエストのホストとパスからプロバイダーを判定し、レスポンスの usage フィールドからトークン数を読み取ります。対象はプロンプト、補完、キャッシュの読み取りと書き込み、推論の各トークンです。

エージェントが捉えたのに読み取れなかった呼び出しも、黙って破棄されることはありません。理由とともに `llm_responses_unparsed_total` に計上されます。

## 4. Pod を特定する { #4-find-the-pod }

プロセスの cgroup からコンテナ ID がわかります。このノードの Pod を watch することで、コンテナをその Namespace、Pod、および Deployment や CronJob などのオーナーワークロードに対応付けます。

## 5. 呼び出しに価格を付ける { #5-price-the-call }

レスポンス内のモデル名を、日付付きの組み込み価格表で検索します。独自の価格や割引を設定していれば、それが上書きで適用されます。呼び出しのコストは、プロバイダーの請求と同じく、入力、キャッシュ読み取り、キャッシュ書き込み、出力に分けられます。価格のないモデルは `llm_unpriced_tokens_total` に計上され、$0 として記録されることはありません。

## 6. エクスポートする { #6-export }

エージェントは、トークン数、リクエスト数、レイテンシー、コストを、Namespace、Pod、ワークロード、モデルのラベル付きで OpenTelemetry メトリクスとして OTLP でエクスポートします。また、呼び出しごとにモデル、Pod、レイテンシー、トークン数を 1 行のログに出力します (リクエストのパスは `debug` レベルで出力)。キャプチャーしたバイト列はエージェントのメモリー内にとどまり、解析が終わると破棄されます。プロンプト、レスポンス、ヘッダー、API キーがエクスポートされたりログに記録されたりすることはありません。

[セキュリティレビュー](security-review.md)には、すべての eBPF プログラム、エージェントに必要な権限、エージェントから見えるものと見えないものが記載されています。
